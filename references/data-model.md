# 数据模型与口径推导

> 本文记录每个数字是怎么算出来的，以及为什么排除掉其他算法。
>
> **数值记号约定（1.13.0 起）**：本文用 `<a>` `<b>` `<n>` 这类占位符代替具体数字，
> 只表达数值之间的关系——大小、单调性、比例、覆盖天数。**全文不含任何一行的真实用量**
> （token 数、积分数、请求数、会话数、金额），也不含从真实用量缩放来的示意值。
> 想看实际呈现效果，见 `assets/` 下三张截图：那是由 `assets/demo/make_ledger.py`
> 用固定种子合成的假账本渲染的，里面的人和数字都不存在。
>
> **模型名与官方单价是产品公开信息，照常写出。** 会变的是「谁用了多少」，那才是要藏的。

## 一、三个数据源

### 1. `~/.workbuddy/workbuddy.db`

| 表 / 字段 | 内容 | 用途 |
|---|---|---|
| `session_usage.credit_json` | `{"<requestId>": 积分}` | 积分主账本 |
| `session_usage.used` / `size` | 当前上下文占用 / 上限 | 上下文占用率 |
| `sessions.id` / `title` / `custom_title` | 会话标题与元数据 | 会话表 |
| `sessions.cwd` | 工作目录 | 工作区兜底 |
| `sessions.deleted_at` / `is_playground` | 删除状态 / 游乐场标记 | 标签 |

**`used` 不是累计量。** 实测它与 `credit_json` 求和之比在两个数量级以上浮动，
与 jsonl 独立核算的会话 token 也不符。它是「当前上下文占用的 token」，
`used / size` 才是占用率。把它当累计积分或累计 token 会把整张报表算歪。

### 2. `~/.workbuddy/projects/**/*.jsonl`

每条消息一行。关键字段都在 `providerData` 下：

| 字段 | 内容 |
|---|---|
| `conversationRequestId` | 关联键，与 `credit_json` 的键同域 |
| `model` | 模型名 |
| `rawUsage.prompt_tokens` | 输入 token |
| `rawUsage.completion_tokens` | 输出 token |
| `rawUsage.prompt_cache_hit_tokens` | 缓存命中 |
| `rawUsage.prompt_cache_miss_tokens` | 缓存未命中 |
| `rawUsage.completion_thinking_tokens` | 思考 token |
| `rawUsage.credit` | 单次调用的积分末次值 |

顶层还有 `timestamp`（毫秒）、`sessionId`、`cwd`、`type`。

### 3. `~/.workbuddy/projects/**/subagents/*.jsonl`

子代理日志。实测其 `requestId` 与主日志**交集为 0**，所以并入主账不会重复计算。

## 二、积分口径：三条通道怎么取舍

本机同时存在三个积分来源：

| 通道 | 来源 | 请求数 | 积分合计 |
|---|---|---|---|
| A | `session_usage.credit_json` | `<nA>` | `<sumA>` |
| B | `type=credit-usage` 记录的 `providerData.credit` | `<nB>` | `<sumB>` |
| C | `rawUsage.credit`（末次值） | `<nC>` | `<sumC>` |

其中 `<nA>` 远大于 `<nB>`，`<nC>` 与 `<nA>` 有大量重叠（见下）。

### 判定过程

**A 与 C 的关系**：两者覆盖的请求大量重叠，重叠区内 **100% 满足 C ≤ A**。
同一请求上，A 普遍是 C 的数倍到数十倍。

→ 结论：**A 是整轮对话（含多次工具调用）的累计结算值，C 只是最后一次调用的值。**
两者不能相加，否则重复计费。C 仅用于补齐 A 里缺失的那部分。

**A 与 B 的关系**：B 只出现在少数请求上，且都在 A 里，值也小于 A。

→ 结论：B 是 A 的子项，**不累加**。

### 最终公式

```
积分 = Σ A + Σ(C for requestId not in A)
     = <sumA> + <sumC_only>
```

覆盖率：约 `<nTotal>` 个请求中 `<nA>` 有积分记录（`<nA>` 个结算值 + `<nC_only>`
个末次值补齐），其余完全无记录。

## 三、token 口径：为什么是求和而不是取最大值

同一个 `requestId` 在 jsonl 里会出现多行。两种可能：

- **流式重复写入** → 应取最大值去重
- **多次独立 LLM 调用**（工具调用循环） → 应求和

### 判定证据

取一条多行请求，看 `rawUsage` 完整序列（记 `<p1> < <p2> < … < <pN>`）：

```
#   type          prompt   compl     hit     miss
3   function_call  <p1>     <c1>      0      <p1>       ← 首次调用，全量未命中
6   function_call  <p2>     <c2>     <p1>    <p2-p1>
9   function_call  <p3>     <c3>     <p2>    <p3-p2>
...
42  message        <pN>     <cN>     <hN>    <pN-hN>    ← 末次调用，几乎全命中
```

三条趋势同时成立，且每一行都满足 `hit + miss = prompt`：

| 列 | 走势 |
|---|---|
| `prompt` | **单调增长**：`<p1>` → `<pN>` |
| `hit` | **单调增长**：0 → `<hN>`，末次已接近 `<pN>` |
| `miss` | **单调下降**：`<p1>` → `<pN-hN>` |

**这是多次独立调用，不是重复写入。** 若为流式重复写入，`prompt` 会原地不动、
只是行数变多；实际观察到的是持续增长。

全量校验：

- 数百条请求中，**零**条出现完全重复的 `(prompt_tokens, completion_tokens)` 对；
- **零**个 `requestId` 跨文件重复出现；
- 绝大多数请求的 `prompt_tokens` 在单请求内单调不减（少量有回落，属上下文压缩/分支切换）。

### 两种口径的差距

| 口径 | token 总量 | 适用场景 |
|---|---|---|
| 求和（累计） | `<Σt>` | 真实用量、计费基础 → **本报表采用** |
| 取最大值（峰值） | `<max_t>` | 单请求上下文规模 → 仅作参考展示 |

单条请求的 `sum / max` 比值远大于 1（典型样本在十几倍量级）。取最大值会低估一个数量级以上。

### 交叉验证

累计口径下 token 与积分呈线性关系：同一条请求算出的 `积分 / token` 比值，
与该模型的全局均价接近。
若改用峰值口径，同一请求会算出高一个数量级的单位积分——明显不合理。

## 四、缓存命中率

```
cache_rate = Σ cache_hit / (Σ cache_hit + Σ cache_miss)
```

累计口径下样本为 **97.2%**。

这解释了核心现象：**token 上亿、积分只有几千**，因为绝大部分输入是缓存命中，
按折扣计价；只有很小一部分未缓存 token 按全价计费。

若按峰值口径算只有 70.0%，会让人误以为缓存效率不高。累计口径才是真实的经济性。

## 五、基准日与环比

### 基准日（anchor）

报表是「截至某日的快照」，截止日即基准日。默认 `auto`：

```
now.hour < 6  →  anchor = 今天 - 1 天
否则           →  anchor = 今天
```

**裁在聚合之前。** 记录先按 `day <= anchor` 过滤，再算五档窗口与各维度，
否则回溯某天时会被后续用量污染。无时间戳的记录（`no_timestamp`）保留在
「全部」里，因为它们无从归属到某一天，但确实发生过。

归档目录用**基准日**命名而非运行日：00:05 跑出来的是前一日的账，
放进前一日目录才符合「一天一份」。

### 两种口径：全量 vs 近 7 天

| 口径 | 用在哪 | 记录池 |
|---|---|---|
| 全量（截至基准日） | KPI 卡片、环比表、每日趋势、活跃日历、最贵单轮请求、按天明细、`summary.all` | `records` |
| 近 7 天 | 官方价预估、按模型、按工作区、按会话 | `_pick(records, anchor-6, None)` → `byModel7` / `byWorkspace7` / `bySession7` |

v1.7 起维度表统一走近 7 天：全量口径下，历史越久、早就不关心的旧会话越占榜首，
「这周谁在烧钱」会被埋掉。换口径时**占比分母同步换成近 7 天积分**（`_week_credit`），
否则占比整体缩水；结论区里「最集中的模型 / 最贵的会话」两句也一并换口径，
避免结论与表格各说一套百分比。联网调用次数同样跟 7 天（`web` 取 `summary.7d.web`）。

### 环比

每个窗口配一个等长上期（闭区间）：

| 窗口 | 本期 | 上期 |
|---|---|---|
| 今日（系统当天 `T`） | `[T, T]` | `[T-1, T-1]` |
| 近 7 日 | `[anchor-6, anchor]` | `[anchor-13, anchor-7]` |
| 近 30 日 | `[anchor-29, anchor]` | `[anchor-59, anchor-30]` |
| 全部 | `[earliest, anchor]` | 无 |

「全部」没有等长上期，所以**环比表里不出现这一行**（v1.7 起）。它的合计值仍然
留在 KPI 卡片和「口径与数据覆盖」区块里，以及 xlsx 的 `汇总` sheet 里——那张表
要的是「总数据」，不是「只列有环比的项」。

**今日档锚的是 `T`（系统当天）而不是 `anchor`**（v1.6 起）。基准日退到昨日时，
今日档照样统计今天——否则「今日」会被改名成「昨日」，用户再也看不到今天花了多少。
上期区间因此也要按**本窗口起点**回推（`_prev_range(start, key)`），按基准日回推会
错开一天。回溯历史某天（`anchor < T-1`）时，今日档退回 `[anchor, anchor]` 并改名
「指定日」。

```
delta% = (本期 - 上期) / 上期      # 上期为 0 或无记录 → None，不补 0
cache_pp = (本期命中率 - 上期命中率) × 100
```

### 覆盖不足判定（重要）

上期窗口的左边界可能早于本机最早记录日，此时上期成交量被天然截断，
环比会虚高到几百上千个百分点。实测例子：

```
本期：<start>~<end>       = <c1> 积分
上期：<start'>~<end'>     = <c2> 积分   ← 但本机最早记录晚于上期起点
→ 上期仅覆盖 <k>/<N> 天，算出的环比会虚高到几百上千个百分点，这是假象
```

处理方式：`prev_covered_days / prev_window_days` 如实记录并在表格标注，
终端打 `*`，**结论区不输出这条环比**。数字保留可查，但不参与判断。
不做任何「按日均外推补偿」——那会把缺失天数变成编造数据。

### 空窗口：0 请求 ≠ 用量塌陷

区间内一条记录都没有时（典型场景：00:05 的定时任务刚跑完，新的一天还没有任何
请求，而「今日」档恒指当天），`_stat_block` 返回的 `empty=True`。此时：

| 位置 | 显示 | 为什么不写 0 |
|---|---|---|
| KPI 卡 | 主数字「暂无」，卡片保留（虚线边框） | 写 `0.00 积分` 会被当成已结算的 0 |
| 环比 | 「本期暂无数据」，其余格 `—` | 上期有量时算出必然是 `-100%`，那是「还没开始用」 |
| 结论区 | 「今日暂无用量记录（数据截至 HH:MM），环比留空而不补 0」 | 归因会指向「所有模型都下降」，全属假象 |
| 终端 | 积分格写「暂无」、环比列写「暂无」 | 与网页同口径 |
| 上期数字 | 照常展示 | 保留对照，不删 |

与「覆盖不足」是两件事：`partial_prev` 是**上期**被记录起点截断，
`cur_empty` 是**本期**根本没有记录。前者照算但标注，后者直接不给环比。

### 当日进行中（partial）

今日档锚的是系统当天，所以它**永远**是「进行中」：`summary.today.partial=True`，
卡片标「截至 HH:MM」。页眉只写日期，不重复时刻——同一次运行里它必然等于
「生成于」的时间，写出来只是把同一个数字印两遍。

回溯历史某天时 `partial=False`，那一档是完整自然日，不是「进行中」。

### 颜色语义

分两类，不能混用同一套色：

| 类别 | 指标 | 上升 | 下降 |
|---|---|---|---|
| 成本类 | 积分 / token / 请求 / 会话 | 更贵 → 红（bad） | 更省 → 绿（good） |
| 质量类 | 缓存命中率 | 更好 → 绿（good） | 更差 → 红（bad） |

### 归因口径

环比只给一个百分比没有行动价值，必须指出**谁贡献了这次变化**。

| 规则 | 值 | 理由 |
|---|---|---|
| 触发阈值 | \|积分变化率\| ≥ 15% | 低于此值是日常波动，硬讲就是噪声 |
| 维度 | 模型、会话各取前 2 | 两个视角足够定位，再多就是刷屏 |
| 份额分母 | **同向合计**，不是净变化 | 净变化做分母会算出「占降幅 142%」 |
| 单项最小占比 | 5% | 滤掉零头 |
| 退化条件 | 积分有 0 时改按 token 归因 | 免费模型期否则会「用量翻倍而指数持平」 |
| 去重 | 会话与模型金额差 1% 内视为同一来源 | 否则同一笔钱报两遍 |
| 反向项 | 单独一句「另有 ±X 抵消」 | 说明为什么净降幅小于主因降幅 |

上期被记录起点截断（`partial_prev`）时**不做归因**：此时所有项都会显示「下降」，
那是「本机用得晚」的假象，不是真实结构变化。

## 六、免费模型与无积分请求

两类情况必须分开，不能混成一个数字：

| 类型 | 表现 | 处理 |
|---|---|---|
| 整模型免费 | `hy4-preview-f`、`hy3`、`step-5-preview`、`hy4-preview`、`qwen3.6` 系列——这些模型的请求**全部**记 0 积分 | 标「免费」，token 照常计入 |
| 无任何记录 | 少数条目，多数是 `model=None` 且 0 token 的元数据行 | 计入 token，报表显式列出条数 |
| 无模型元数据 | 少量条目，0 token 但带极小积分 | 归入「(未知模型)」，不影响总量 |

免费模型合计 `<n>` 次请求、`<t>` token、0 积分。这部分是纯粹的账面节省。

> 分得清「整模型免费」与「偶发 0 积分」很要紧：前者是定价政策，后者可能是记账缺失。
> 把两者混成一个数字，会让人误判成「平台漏记了」——1.12.1 就吃过这个亏。

## 七、官方价预估（人民币）

### 为什么要单独一层

本机账本里**没有任何单价字段**（全量字段扫描确认），积分是平台结算值，无法反推单价。
所以「等值费用」只能来自**外部的官方价目页**，与本机 token 相乘得到。
这决定了它只能是参考值：分子（token）是本地统计，分母（单价）是外部数据。

### 价目表（2026-10-24 检索）

单位：**人民币元 / 百万 token**，每格三数为「缓存命中输入 / 未命中输入 / 输出」。

| 模型 | 官方产品名 | 高峰 | 空闲 | 来源 |
|---|---|---|---|---|
| `deepseek-v4.1-flash` | DeepSeek-V4.1-Flash-1017 | 0.04 / 2.00 / 8.00 | 0.02 / 1.00 / 4.00 | api-docs.deepseek.com/zh-cn |
| `deepseek-v4-pro` | DeepSeek-V4-Pro-0813 | 0.30 / 9.00 / 27.00 | 0.15 / 4.50 / 13.50 | api-docs.deepseek.com/zh-cn |
| `glm-5.3-flash` | GLM-5.3-Flash | 统一 0.23 / 0.80 / 2.80 | 同左 | bigmodel.cn |

**全部读官方中文页直给的人民币价，不做美元折算。** v1.5 及以前 V4-Pro 是按
美元价 × `--fx`（默认 7.10）算的（0.31 / 9.37 / 28.12），与官方人民币价差约 4%——
折算把一个本来精确的数变成了近似的数，已改。`--fx` 参数保留但不再影响任何计算。

### 峰谷判定

```
高峰 = 周一至周五 且 非法定节假日 且 本地时间 ∈ [09:00,12:00) ∪ [14:00,18:00)
空闲 = 其余全部时段，价格 = 高峰 × 0.5
```

三个实现要点：

1. **节假日表内置**（`pricing.CN_HOLIDAYS`，源自国办发 2026 年放假通知）。
   2026 年有 7 段：元旦 1/1–1/3、春节 2/15–2/23、清明 4/4–4/6、劳动 5/1–5/5、
   端午 6/19–6/21、中秋 9/25–9/27、国庆 10/1–10/7。
   其中 9/25、10/1、10/2、10/5、10/6、10/7 是**落在工作日的节假日**，
   漏判会把费用算高一倍。
2. **调休上班的周六/周日不按高峰算**：DeepSeek 原文只写「周一至周五」，
   照原文执行。故 2026/9/20、10/10（调休上班）仍按空闲价。
3. **缺表年份会报缺口**：`pricing.annotate()` 返回 `missing_holiday_years`，
   报表打 ⚠，这些年份的节假日按高峰价计（偏高）。跨年前记得补表。

### 输入拆分

`prompt_tokens` 通常 = `cache_hit + cache_miss`，但上游有时只报命中数。
差额按**未命中（全价）**计——宁可高估，也不要给出偏低的价格让人误判成本。
若两者之和已超过 `input`，则直接信任 hit/miss（说明 `input` 只报了非缓存部分）。

### 未定价模型

`hy*` / `step-5-preview` / `space-bunny`（订阅制）、`qwen*`（本地或量化）
没有官方公开 token 单价，`cost_priced=False`，**不参与任何折算**。
报表给出**费用覆盖率**（有价 token / 全部 token）。它通常**不是 100%**——未定价模型
那部分 token 永远算不进价，覆盖率就是用来提醒这一点的。

### 结构（具体呈现见 `assets/pricing.png`）

| 模型 | 有价 token | 积分 | 价估 | 全高峰价 |
|---|---|---|---|---|
| glm-5.3-flash | `<t1>` | `<c1>` | `<m1>` | `<m1_peak>` |
| deepseek-v4.1-flash | `<t2>` | `<c2>` | `<m2>` | `<m2_peak>` |
| deepseek-v4-pro | `<t3>` | `<c3>` | `<m3>` | `<m3_peak>` |
| **合计** | `<Σt>` | `<Σc>` | **`<Σm>`** | `<Σm_peak>` |

「全高峰价」是把同样的 token 全部按高峰时段牌价重算一遍的结果，**一定高于价估**，
差额就是错峰省下的钱。各模型峰时占比不同，所以两者之间的折扣幅度也不同。

**注意积分与费用不成比例**：同一笔 token 在不同模型上的积分系数并不相同，
因此积分高的模型价估未必高——它取决于各自牌价与峰时占比。
这正是不能拿积分去反推价格、也不能拿价格去反推积分的原因。

### 联网检索 / 抓取：只报次数，不折钱

价估表末尾单列一行「未计入上表」，内容固定为：

> 联网检索 / 抓取 `<n>` 次（Search `<ns>` · Fetch `<nf>`），只统计了调用次数，仅作参考、不能当账单

| 项 | 值 |
|---|---|
| 计数来源 | `function_call` 记录的 `name ∈ {WebSearch, WebFetch}`，按 `(sessionId, callId)` 去重 |
| 裁剪 | 与 records 同口径：先按基准日裁，再按 `--days` 裁 |
| 量级 | 只报次数，不报具体值——它随机器和使用习惯变化，写死任何数字都是误导 |
| 金额 | **不给金额**。WorkBuddy 侧无公开按次牌价，任何折算都是借来的数 |

两条必须写在报表里的限制：

1. 本机日志只数得到**工具调用次数**，分辨不出它是否真的走了联网接口，
   所以只能作参考，不能当账单。
2. 这一项**不属于** token 单价模型，任何时候都不并进合计。

> **口径事故留档（2026-10-24 修正）**：v1.2.0–v1.4.0 曾写「Search / Fetch 均按
> US$0.75 / 千次成功请求计费」，并据此报出「本期若干元、此后同量若干元」。该单价
> 出处在 **DeepSeek API 文档** `Search & Fetch Pricing`，原文限定场景是「通过
> DeepSeek Harness / Claude Code / Codex 调 DeepSeek API 时，服务端工具调用已经打到
> DeepSeek 的 Search / Fetch 接口」。本报表数的是 WorkBuddy 自己的 `WebSearch` /
> `WebFetch`，两者计费主体不同，乘出来的数不成立，已整体移除（`pricing.SEARCH_FETCH`
> 与 `search_fetch_cost()` 一并删除）。

### 刻意不做的：价目表「已 N 天未更新」提醒

页脚已经给出检索日期与来源链接，再加一个天数阈值只是噪音，且阈值定多少都无依据。
官方调价时手动改 `RATE_CARDS` 即可。

## 八、已知局限

1. **官网数字可能与本报表有差**：报表读本地账本快照，平台尚未回写 `credit_json`
   的请求会缺积分。报表「无积分请求」一栏会显式给出条数与 token 量。
2. **少量长会话（单会话数百次调用）token 偏低**：用积分反推，其应有 token 约为实际
   记录的 3–8 倍。在作者的一次样本中，这类会话约占个位数百分比的 token、两成左右的
   积分，比例随使用模式差异很大。原因推测是长会话日志
   有部分轮转/截断。已在报表里如实呈现，**明确不做任何估算补偿**——
   按比例放大能凑出更像样的数字，但不可复现。
3. **本机账本没有单价、余额、TTFT**（全量字段扫描确认）。第七节的价格全部来自
   外部官方页面，不是账本里的数据；官方调价后必须手动更新 `RATE_CARDS`。
4. **联网项只有次数、没有金额**：WorkBuddy 侧无公开的按次牌价，故不折算、不进合计。
   这项若将来被平台按次收费，实际账单会比价估高出这一块。
5. **时区固定 +08:00**：跨时区使用需要改 `collect.py` 的 `TZ`，
   峰谷判定也依赖它。

### 上下文压缩：只能靠 prompt 回落间接识别

「经济模式」在上下文接近上限时会把历史摘要化，压缩那一次**按普通模型调用计费**，
其消耗已经包含在 token 与积分总量里，报表不额外补也不扣。

问题在于**日志里没有压缩事件**：全量 `type` 只有
`function_call` / `function_call_result` / `reasoning` / `message` /
`file-history-snapshot` / `session-meta` / `credit-usage` / `ai-title` /
`resend-fork-notice` 九种，没有一种是它。压缩留下的唯一痕迹是同一个 `requestId` 内
`prompt_tokens` 的**突然回落**。

判定与估算（`collect._find_compactions`）：

| 项 | 做法 | 代价 |
|---|---|---|
| 判定 | 同一 `requestId` 内，某轮 prompt 比上一轮跌 **≥15%** 即认作一次压缩 | 阈值靠经验：正常轮次只增不减，抖动是个位数百分比；回落实测都在撞到上下文天花板之后，幅度远大于 15% |
| 省下量 | `回落幅度 × 该请求在压缩之后的剩余调用次数` | 假设「不压缩的话被砍掉的上下文会一直带着」，而真实情况它还会继续增长 → **偏保守** |
| 分母 | 该窗口的**输入** token（不是输入+输出） | 压缩砍的是送进去的上下文，与吐出来多少无关 |
| 性质 | **毛估算** | 省下的输入 token 大部分本会命中缓存，故**不能等同于积分节省** |

`resend-fork-notice`（用户重发 / 分支）也可能造成 prompt 回落，目前与压缩合并计入，
无法区分——两者在数据上长得一样。

### 删会话：token 在、积分 0

删除一个会话时，`session_usage` 里对应的结算行会跟着消失，但
`projects/**/*.jsonl` 的日志还在磁盘上。于是这些请求**token 照算、积分算 0**。

偏差**只有一个方向：积分只少不多**，不会虚高。「口径与数据覆盖」把已删会话的个数、
它们的 token、以及其中「有 token 但没有积分结算」的部分单独列出，便于判断差额来源。

判定只用 `sessions.deleted_at`，**不用**「`session_id` 不在 `sessions` 表里」：
子代理会话本来就不进 `sessions` 表，拿后者当删除判据会把活着的子代理会话
误判成「已删除」，凭空造出一条不存在的偏差。

## 九、复现验证

```bash
# 取数层单独跑，核对覆盖数字
python ~/.workbuddy/skills/wb-usage-report/scripts/collect.py

# 价目卡与峰谷判定自查
python ~/.workbuddy/skills/wb-usage-report/scripts/pricing.py

# 期望输出（各计数随使用变化，这里不写死具体值）
#   requests      : 总请求数
#   with credit   : 其中有积分记录的
#     ledger      : credit_json 结算值补齐的
#     raw patch   : 末次值补齐的
#   no credit     : 完全无记录的
#   subagent reqs : 子代理请求
```

`pricing.py` 自查应输出：周六 10:30 → 空闲、周五 10:30 → 高峰、
周五 13:00 → 空闲、**周一 10:30（国庆）→ 空闲**。

数据会随使用变化，量级应保持稳定。**恒等式**：`ledger + raw patch == with credit`。
若不等，说明 `_classify_credit` 的优先级逻辑被破坏——这条校验关系比具体数字更值得记。
